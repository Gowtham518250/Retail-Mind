# Voice billing & AI Query: evaluation notes

What was measured, how, and what the numbers do **not** mean.

## 1. Phantom speech on silence (the "I said nothing but it typed text" bug)

**Root cause (three links):**
1. Whisper was called with a language hint plus a shop-vocabulary prompt. For silence/noise Whisper still emits fluent text; the backend requested `verbose_json` but never read `no_speech_prob`, `avg_logprob` or `compression_ratio`, so it trusted any text.
2. The translation LLM converted gibberish into a plausible English sentence.
3. The extraction prompt said "always preserve each recognized product as a line", so that sentence became bill lines.

**Fix (defence in depth):**
| Layer | Where | Rule |
|---|---|---|
| App level gate | `lib/voice_activity_gate.dart` | Silence / taps are not uploaded (level samples vs noise floor). Fails open if levels unreadable. |
| ASR confidence guard | `voice_asr_guard.py` (used by `/voice-billing/parse-audio` and AI-Query voice) | Drops segments with high `no_speech_prob`, low `avg_logprob`, repetitive `compression_ratio`, known silence phrases ("Thanks for watching"), prompt echo, too-short speech. Text is rebuilt from surviving segments only. |
| Translation | prompt | May return an empty string for unintelligible input -> existing "could not translate" path. |
| Extraction | prompt + `custom_name_is_grounded` | A non-catalog line is only kept if its name was actually in the transcript. |

**Evidence level:** unit tests with realistic payload fixtures (`tests/test_voice_asr_guard.py`, 33 tests) and endpoint tests proving silence returns 422 and never reaches the LLM. **No labelled audio was available, so there is no measured false-reject / false-accept rate and no WER.** The thresholds (`GuardThresholds`, `VoiceActivityGate`) are engineering defaults, stricter than Whisper's reference (`no_speech>0.6 AND avg_logprob<-1.0`) because a wrong bill line costs more than a re-record. To calibrate: record ~100 clips each of (a) silence/room noise/cough, (b) real orders in shop noise, run them through `assess_transcription`, and tune on the false-reject/false-accept trade-off. Logs contain only the rejection reason, never speech text.

## 2. Voice billing post-processing benchmark

`tools/voice_billing_eval.py`, cases generated by `tools/generate_voice_billing_eval_cases.py` (development set) and `tools/generate_voice_billing_heldout_cases.py` (held-out set, different catalog/products/phrasing, frozen before it was run).

Scope: the deterministic layer *after* LLM extraction (catalog resolution, ambiguity, unit conversion, quantity grounding, replay protection). The LLM is **simulated identically for old and new code**, so the delta isolates the new logic. It does not measure ASR or LLM quality.

| Set | cases / items | metric | before | after |
|---|---|---|---|---|
| development | 206 / 246 | product decision | 82.11 % | 100 % |
| | | line-item (product+qty+unit+grounding) | 67.07 % | 100 % |
| | | bill total | 82.86 % | 100 % |
| held-out (run once) | 39 / 45 | product decision | 84.44 % | 100 % |
| | | line-item | 71.11 % | 100 % |
| | | bill total | 83.87 % | 100 % |

Caveats: both sets are synthetic and self-authored, and the development-set resolver was tuned against its own failures. 100 % is therefore "passes the cases I could think of", not production accuracy. Deterministic latency rose slightly (mean ~0.6 -> ~0.8 ms), negligible against the network calls.

**Label correction (disclosed):** cases such as "2 bottles of a per-litre product" were originally labelled "convert", then relabelled to expect a *unit mismatch* flag, because guessing a bottle size would be a financial-correctness risk.

## 3. AI Query date-scope benchmark

`tools/ai_query_date_eval.py` + `tools/generate_ai_query_date_cases.py`. Expectations are derived independently of the code under test; the clock is frozen per case as a UTC instant so IST/UTC day boundaries and month/year/leap transitions are exercised. Measures only the deterministic date resolver; **not** SQL generation, translation or answer quality (those need a database and an LLM key).

| Set | cases | accuracy before -> after | silently wrong date | no date filter, no clarification |
|---|---|---|---|---|
| development | 188 | 69.68 % -> 100 % | 10 -> 0 | 1 -> 0 |
| held-out, **first run** | 26 | 30.77 % -> 76.92 % | 1 -> 0 | 5 -> 4 |
| held-out after closing the gaps it exposed | 26 | 100 % | 0 | 0 |

The held-out set stopped being held-out once I fixed what it exposed, so the **first-run 76.92 %** is the honest generalisation figure.

Behavioural changes: "day before yesterday" no longer returns yesterday; "15 October / 15th oct / oct 15" and abbreviations; ranges "1 Oct to 15 Oct"; whole months ("in October", year inferred as most recent past); "in 2025"; "since D"; "N days ago"; "past week". A date with no year that would fall in the future resolves to the most recent past occurrence. Weekday names, "on the 15th", "last 24 hours", quarters and future months now trigger a clarification instead of running with **no date filter**. Month words only count after "in/during/for", so "march rice brand" is not a date.

Relabelled case (disclosed): "sales in february 2028" was first labelled *resolved*; at a Nov-2026 clock it is a future month, so *clarify* is correct. Leap-year coverage moved to a March-2028 clock.

## 4. Not done / limitations
* Follow-up questions ("what about yesterday?") are **not** implemented; the app sends each query independently.
* No Flutter/Dart SDK could be installed in the build sandbox (download blocked), so Dart code and `test/voice_activity_gate_test.dart` were **not executed**; the gate's expected outcomes were re-derived in Python. Run `flutter test` before release.
* No real-audio, real-LLM or real-database measurements were possible.
* 8-9 pre-existing backend test failures (OTP/billing/inventory-sync; DB-state dependent, flaky run to run) are identical on the untouched base commit.
